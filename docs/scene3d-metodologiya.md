# Сцены-сплаты: методология конвейера (для валидации и развития)

Записано 18.08.2026 (вечер) по требованию оператора: компактно, как всё
устроено, без ультра-деталей. Ниже раздел «Валидация» — вердикт независимого
аудита на чистом контексте. НИЧЕГО из найденного пока не исправлялось.

## Цель

Зоны горы как фотореалистичная 3D (гауссовы сплаты), геопривязанные и
встроенные слоем в воксельный «Полёт 3D». Для ориентировки; отсмотр и
координаты — только по исходникам.

## Конвейер (скрипты в analysis/scene3d/)

1. **Выборка кадров зоны** — `extract_zone.py` (общая) / `extract_koshki.py`
   (пилот). Источник: кеш плеера flights/*/meta.json — сэмплы каждые 2 с с
   позой подвеса и проекцией центра кадра в рельеф (ctr). Кадр берётся, если
   ctr в bbox зоны и дистанция ≤ порога; прореживание на ролик и глобально;
   отбраковка смазанных (варианс лапласиана < 25 на даунскейле 640).
   Опц. фильтр подстроки имени ролика (день/камера). Кадры 1920×1080 из
   видео по POS_MSEC.

2. **Позы камер (SfM)** — `sfm_zone.py`: pycolmap 3.13, SIFT
   (max_image_size 1920), exhaustive matching, инкрементальная сборка с
   порогами под телевик: `init_min_tri_angle=4°` (дефолт 16° не даёт
   инициализации на узком FOV), `abs_pose_min_inlier_ratio=0.15`,
   `init_max_reg_trials=4`. Камера SIMPLE_RADIAL на кадр (зум плавает).
   Из подмоделей берётся крупнейшая (≥25 камер).
   - Тупик (задокументирован): триангуляция в телеметрийные позы
     («план Б», `triang_koshki.py`+`refine_koshki.py`) даёт «острова» —
     красивая репроекция при медиане наблюдений 0 на кадр. Телеметрия
     (метры/градусы) слишком груба для прямой триангуляции телевика.
     Диагностический признак: `медиана img.num_points3D()` и проекция
     всех точек в кадр.
   - Зависание на месте (нет базы) не собирается в принципе; макро-кадры
     дорегистрированы в жёсткую модель ослабленными порогами
     (`register_koshki.py`: min_num_inliers 12, ratio 0.05, max_error 16).

3. **Геопривязка** — `georef_scene.py`: подобие Umeyama центры камер модели ↔
   телеметрия тех же кадров (ENU от якоря = среднего телеметрии), плюс
   псевдоточки «центр + ось взгляда × 60 м» против коллинеарных треков;
   2 итерации с отбросом хвоста невязок (порог max(2×p80, 3 м)). Опц.
   `--only=подстрока` — подгонка по одному когерентному ролику (GPS-дрейф
   между роликами портит общую). Выход: anchor + T(4×4 scene→ENU) + rms_m.
   Зоны с RMS > 20 м помечаются rough и в слое не рисуются.

4. **Тренировка** — Brush 0.3 (Metal). Датасет: `export_brush.py` — модель в
   ЛЕГАСИ-текст COLMAP (новый формат pycolmap 3.13 c frames.bin Brush молча
   читает как мусор) и PINHOLE (fx=fy=f, дисторсия отброшена; SIMPLE_RADIAL
   Brush не понимает). Кватернион pycolmap — (x,y,z,w), в images.txt пишется
   (w,x,y,z). 20-50k шагов, max-splats 3-8 млн. Контроль качества:
   `--eval-split-every N --eval-save-to-disk` — рендеры отложенных кадров
   сравниваются с фото ГЛАЗАМИ (единственный честный тест; веб-вьюер для
   оценки качества модели не использовать).

5. **Конвертация для веба** — `ply2splat.py`: 3DGS ply → .splat (32 Б/сплат:
   pos 3×f32, scale 3×f32, RGBA u8 из SH0, кватернион 4×u8). Фильтры:
   op ≥ 0.02; «иглы» s2/s1 ≥ 8 — вон (s2/s0 НЕЛЬЗЯ — это блины-поверхность);
   гиганты > 3 м — вон. При превышении лимита — РАВНОМЕРНАЯ случайная
   выборка (отбор «по весомости» выбрасывает мелкую деталь — «мазня»).
   Порядок в файле по весомости — только для прогрессивной загрузки.
   Обрезка фона: `crop_scenes.py` — сфера R вокруг якоря (фон зоны после
   подобия ложится с промахом сотни метров и размазывается).

6. **Слой в Полёт 3D** — порт ядра antimatter15/splat в polyot3d_template:
   воркер-сортировщик (счётная сортировка по глубине) как есть; вершинный
   шейдер изменён: центр и глубина сплата — из клип-пространства ДВИЖКА
   (совместимость с depth-буфером рельефа), ковариация — в конвенции
   оригинала (view с флипом z), y-компонента экранного смещения инвертирована,
   множитель размера НЕ добавлять (2 уже в кваде ±2). Блендинг back-to-front
   (reverse depthIndex) с premultiplied alpha. Сцены рисуются дальние→ближние.
   Матрица scene→grid: G = A·T, A — ENU→сетка (x=E/BX, y=U/BX, z=−N/BX,
   якорь по формулам payload; ВСЕ вычисления в float64 до локализации).
   Ленивая подгрузка сцен по близости якоря (~2.2 км), общий прогресс-бар.

## Известные слабости (честно, до аудита)

- Геопривязка по камерам, не по рельефу/GCP: RMS 2-35+ м, у вырожденных
  треков хуже; сцены могут «тонуть»/«парить» относительно DEM.
- Разные дни не сшиваются (освещение) — зоны одного дня.
- Перекрывающиеся сцены двоятся (нет межсценного z-порядка на сплат).
- Иглы на краях покрытия остаются; фильтр — грубая эвристика.
- Макро-ракурсы (в упор) мыльные: позы с ослабленной регистрацией,
  mm-масштаб требует субпиксельной точности.
- История самоисправлений (для контекста аудита): float32-квантование
  меркатора; фокусный fallback развалил BA; телеметрийные «острова»;
  формат Brush; фильтр игл по s2/s0 (чёрный экран); отбор по весомости
  (мазня); лишний ×2 размера; дедлок воркера.

## Валидация (аудит на чистом контексте, 18.08, ничего не исправлялось)

### Подтверждено корректным ✅
Umeyama; кватернион (x,y,z,w)→(w,x,y,z); легаси-экспорт; распаковка ply
Brush и SH0/opacity/quat; crop в ENU-метрах; scene→ENU→сетка (1e-14);
порт шейдера (фокусные, ковариация, y-флип, глубина); эквивалентность
блендинга reverse+over ≡ front-to-back under.

### Ошибки ❌ (по убыванию тяжести)
1. **Дисторсия отброшена неправомерно** (export_brush): k до 0.54, смещение
   в углу кадра медиана 22-25 px, максимум 183 px → Brush учится на
   несогласованной проекции: мыло периферии, сдвиги сплатов на метры.
   Лечение: андисторшн кадров перед экспортом.
2. **Фильтр «гигантов > 3 м» — в сценических единицах, не в метрах**
   (ply2splat): реальный порог 17-363 м в зависимости от масштаба сцены —
   фильтр фактически не работает (часть «месива»).
3. **Правило rough (RMS>20 м) нигде не реализовано** — флаг ставился
   вручную; очередь задеплоит следующую плохую зону сама.
4. **RMS геопривязки не защищён от вырожденности**: 7 камер с короткой
   базой дают масштаб 0.002 при RMS 0.08 м — «идеальная» метрика у
   мусорного преобразования. Нужны: разброс центров, сверка масштаба с
   телеметрийной базой, RMS только по камерам (сейчас смешан с
   псевдоточками: у linia-13 «RMS 8 м», по камерам p90 = 26 м).
5. **Идемпотентность очереди сломана** переименованием частей при crop:
   перезапуск очереди пересчитает всё и затрёт обрезанные сцены.
6. Смешение камер и псевдоточек в used/RMS; финальная T не переподогнана
   по финальному keep.
7. Парсинг CLI georef (--only vs позиционный якорь) конфликтует.

### Главные методологические риски ⚠️
- Привязка только по GPS/баро камер, без сверки с DEM/известными точками —
  системные сдвиги 10-30 м даже у «хороших» зон; сверка дешева и не сделана.
- Ослабленные пороги SfM → ложные регистрации → 40% зон в браке.
- Дыры покрытия и нумерация зон завязаны на KML-полилинию (молчаливые
  пропуски, переномерация при правке линии).
- Кадр↔телеметрия: POS_MSEC-сик неточен (± кадры → метры позы).
- Вьюер: сцены/воркеры не выгружаются (память до ГБ), сорт на каждую
  матрицу; в поясе 3.4-4.5 км от якоря сортировка стухает.

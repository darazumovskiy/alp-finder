# Концепция: показ отснятой горы «как есть» (иерархия честности)

Записано 18.08.2026. Цель, к которой идём: **вся гора в 3D, где каждое
отснятое место показано так, как его видел дрон** — в максимально честном
и детальном виде, доступном по материалу. Не учебная задача: слои используются
для отсмотра, ориентировки штаба и планирования дозасъёмок.

## Принцип

В каждой точке горы показываем **лучшее из возможного** для этой точки,
с автоматическим переключением (целевая картинка, «иерархия честности»):

| ур. | слой | что это | честность |
|---|---|---|---|
| 1 | **Сплаты зоны** | настоящая 3D-реконструкция (гауссовы сплаты): валуны, снежники, вещи как объёмные объекты, свободный облёт | максимум: геометрия + фото |
| 2 | **«Глазами дрона»** | настоящий кадр, проецируемый на рельеф из позы дрона, где он был снят | честно у трека, «плывёт» вдали от позы |
| 3 | **Обои (ортомозаика)** | лучший кадр на каждый кусочек земли, натянутый на рельеф | фото есть, геометрия грубая (DEM 8 м) |
| 4 | **Голый рельеф** | воксельная раскраска по высоте/уклону | «тут не снято» — тоже информация |

Уровни 2–4 уже живут в «Полёт 3D» (polyot-3d.html) и включаются галками;
уровень 1 — в работе (пилот). Комбинирование в единый автоматический
переключатель — план после пилота.

## Что уже есть (сделано, задеплоено в тим-версию)

- **Ортомозаика** (`analysis/build_ortho.py`, док: docs/video-analysis.md,
  раздел «Ортомозаика»): пирамида меркаторных тайлов из 81 ролика,
  адаптивное разрешение до ~0.7 см/пикс, 2653 кадра, привязка ~7 м на
  лучших ракурсах (проверено по рюкзаку). Слои: 3D «обои» + оверлей на
  2D-карте (зум до 25).
- **«Глазами дрона»** (`build_polyot3d.py` слой eye + шейдер в
  polyot3d_template.html, док: docs/polyot-3d-glazami-drona.md):
  6 кадров-проекторов вокруг прицела, связка стабильная, кроссфейды.
  Дорабатывается ОТДЕЛЬНОЙ сессией (якорь на прицел, гистерезис в метрах —
  см. док, он поддерживается актуальным той сессией).
- **Воксельный рельеф** — движок Николая (kurumdy-3d), HMA 8 м + DSM-патчи.

## Итог ночи 18.08: пилот сплатов РАБОТАЕТ (сцена 16.08)

Рабочий конвейер (см. коммит cf96b02, скрипты в `analysis/scene3d/`):
инкрементальный COLMAP с порогами под телевик → модель подлётного облёта
(56 камер, 41 тыс. точек) → экспорт легаси-PINHOLE (`export_brush.py`) →
Brush 30 тыс. шагов → **eval-рендеры на отложенных кадрах ≈ фотографии**
(скальные пояса, снежные полки — узнаваемо; «иглы» на краях покрытия).
Вьюер — `scena-3d.html` (в тим-версии), сцена из двух частей в `scenes/`.

Грабли, чтобы не наступать снова: (1) телеметрийные позы слишком грубы для
прямой триангуляции телевика — модель рассыпается на островки при красивой
средней репроекции, проверять `медиану наблюдений на кадр`; (2) новый формат
моделей pycolmap 3.13 (frames.bin) Brush не читает — только легаси-текст +
PINHOLE; (3) зависание на месте (114520) в SfM не собирается — нет базы;
такие кадры в сплаты не идут (но остаются в отсмотре и «глазами дрона»).

## Что делается сейчас (эта сессия)

**Пилот сплатов на сцене 16.08 «кошки»** (три ролика облёта + 10 прицельных
LRF-фото; ботинки, ледоруб, «голень»). Конвейер, файлы в `analysis/scene3d/`:

1. `extract_koshki.py` — выборка кадров по телеметрии (камера смотрит на
   сцену, <300 м, резкие) → 431 изображение;
2. `sfm_koshki.py` — SIFT + exhaustive matching (CPU, готово: 18 208
   верифицированных пар, все источники сшиты);
3. `map_koshki.py` — сборка поз камер. Грабля: дефолтный
   `init_min_tri_angle=16°` не годится для телесъёмки (углы триангуляции
   на порядок меньше) — mapper час собирал огрызки по 10–12 кадров.
   С порогом 4° и мягкой регистрацией модель доросла до 86+ камер (идёт);
4. далее: привязка модели к мировым координатам по телеметрии
   (RANSAC-подобие, как у C C в `analysis/scene3d/src/scene3d.py`),
   тренировка сплатов **Brush** (~/tools/brush, Metal/GPU, headless CLI),
   вьюер-страница в тим-версии, ссылка из карточек точек сцены.

План Б, если incremental mapper не соберёт всё: начальная модель прямо из
телеметрии (позы известны с точностью м/градусов) → триангуляция матчей →
только bundle adjustment. Надёжнее для вырожденной телесъёмки.

## Планы после пилота

- **Вся гора = мозаика зон** 200–500 м; выборка кадров на зону — автоматом
  по телеметрии (готовый механизм в extract_koshki обобщается). Зоны с
  богатой съёмкой дадут плотную 3D, дальние — рыхлую; это честная карта
  качества покрытия и подсказка для дозасъёмок.
- **Вьюер**: подгрузка сплат-зон по мере полёта (та же логика, что окна
  ортотайлов); уровень 1 в иерархии, фолбэк на «глазами дрона» → обои.
- **Счёт**: одна зона ≈ час-два на Маке (CPU-позы + GPU-тренировка).
  Вся гора — десятки часов фоном, либо GPU-машина: C C с RTX (в контуре)
  или аренда — решение оператора (вынос кадров наружу, приватность).
- Идея-гибрид (оператор, 18.08): комбинировать сплаты с «глазами дрона»,
  чтобы в каждой точке выбиралось лучшее доступное — и есть куда падать,
  когда сплатов зоны нет.

## Ограничения, о которых помнить

- **Производные слои — не для поиска** (вопрос оператора 18.08). Сплаты —
  подгонка под наши кадры (не генеративная модель, ничего не выдумывает),
  но потеря при усреднении реальна: предмет из 1-2 кадров, тонкое (шнур),
  шевелящееся (ткань) может размыться или пропасть. Отсмотр и поиск — ТОЛЬКО
  по исходным кадрам и сканам; сплаты/обои/«глазами дрона» — ориентировка,
  навигация, геометрия. Увидел подозрительное в производном слое →
  проверяешь по исходникам этого места.
- Сплаты хороши там, где многоракурсная съёмка; один дальний пролёт даст
  мыло — и это не чинится без дозасъёмки.
- Всё считается и публикуется ТОЛЬКО в закрытом контуре (CLAUDE.local.md):
  локальный счёт, деплой deploy_private.sh, никаких внешних сервисов без
  явного решения оператора.
- Координаты для штаба — только через строгий конвейер (docs/koordinaty-
  status.md); визуальные слои — для отсмотра и ориентировки.

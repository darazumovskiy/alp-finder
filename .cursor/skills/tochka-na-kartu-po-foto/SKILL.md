# Точка на карту по фото/скриншоту

Вход: фото или скриншот плеера (обычно из TG: `data/telegram/<слаг-темы>/<msg_id>.jpg`)
с заявкой «в этом видео на этой секунде виден объект». Выход: карточка в `POINTS`
`analysis/viewer/build_map.py`, синхронизированные доки, опубликованная карта.

Рабочий python — только `analysis/.venv/bin/python` (cv2, numpy, tifffile);
системный python без cv2.

## 1. Атрибуция видео и таймкода

- Имя видео (`DJI_YYYYMMDDHHMMSS_NNNN_Z.MP4`) — из текста заявки или заголовка
  плеера на скрине. Найти файл: `rg "<токен>" scripts/manifest.tsv docs/drive-inventory.md`,
  `ls data/drive/*/`. Имя даёт только дату/идентификацию; таймзоны в расчётах
  не участвуют — телеметрия индексирована секундами от начала видео.
- Длительность сверить: `ffprobe -v error -show_entries format=duration -of default=nw=1 <видео>`.
- Таймкод с UI плеера: левая цифра — текущее время; **правая — оставшееся время,
  а не длительность**. Позиция ползунка в процентах — перекрёстная проверка.
- **Заявленному таймкоду не доверять** (бывало «3.54» при реальных 4:04):
  реальный кадр искать развёрткой + SIFT-матчем (шаг 3).

## 2. Выемка кадров

```bash
mkdir -p analysis/fullframe/<слаг-эпизода>
for t in $(seq T0 2 T1); do
  ffmpeg -v error -ss $t -i <видео> -frames:v 1 -q:v 2 analysis/fullframe/<слаг>/t${t}s.jpg -y
done
```

Сначала грубая сетка вокруг заявленного таймкода (± десятки секунд, шаг 2 с),
после матча — точные секунды. Кадры подтверждённых вещей — в
`docs/nakhodki/frames/<basename>_MMmSSs.jpg`. Кропы для карточки:
`ffmpeg -i tNNNs.jpg -vf "crop=W:H:X:Y,scale=...:flags=lanczos" <слаг>_zoom.png`.

## 3. SIFT-матч скрина с кадрами

Одноразовый скрипт на OpenCV (SIFT + FLANN, гомография RANSAC):

- маскировать панели плеера (верхние ~30 px, нижние ~90 px) и красную разметку
  волонтёра (порог `r>120, r-g>60, r-b>60`);
- прогнать скрин по всем кадрам развёртки, выбрать максимум инлаеров
  (надёжный матч — сотни, ориентир ≥100);
- перенести гомографией центр разметки в пиксель кадра `(px, py)` — он нужен
  для трассировки луча;
- результат проверить глазами: положить рядом кроп кадра и скрин.

Зум-скрины матчить по указанной crop-области, дубликаты скринов ловить по
размеру файла.

## 4. Телеметрия

Сайдкар `<видео>.MP4.gps.tsv` рядом с видео: `time_s` (секунды от начала),
`lat`, `lon`, `alt_m`, `alt_rel_m`, `ac_yaw`, `ac_pitch`, `ac_roll`, `gb_yaw`, `gb_pitch`.
Нет сайдкара — сгенерировать: `scripts/dji_meta_gps.py` (protobuf-поток DJI,
работает и там, где нет SRT). Lookup:

```bash
awk 'NR==1 || ($1+0)>=219.5 && ($1+0)<=220.5' <видео>.MP4.gps.tsv
```

Обратная задача (по координате найти момент сближения) — haversine по всему
tsv; помнить: сближение ≠ камера смотрела на объект, проверять `gb_yaw/gb_pitch`.

## 5. Координата — лестница надёжности (у каждой ступени своя σ)

1. **Дальномер/триангуляция штаба** — если есть, брать её (`coord=LRF`), σ ≈ 10 м.
   В видеотелеметрии M30T лазера НЕТ (проверено разбором protobuf-потока и SRT,
   15.08) — LRF есть только в XMP фотографий.
2. **Триангуляция ≥2 ракурсов** — `analysis/triangulate.py`:
   `find <lat> <lon> <alt>` ищет по всему архиву кадры, видящие точку, с базой;
   пиксель во втором кадре — SIFT по окрестной скальной текстуре или глазами;
   `solve photo:<jpg>:<px>:<py> video:<mp4>:<t>:<px>:<py> …` печатает координату,
   остатки по лучам и σ-эллипсоид. Остаток >10 м = не тот объект/пиксель.
   **Обязательна** для пологих лучей (<~15° к горизонту), находок у кромок
   и находок на панорамах (там лазер смотрит по сетке, не на объект).
3. **Надирный кадр** (`gb_pitch` ≈ −90°) — σ ≈ 10 м, но только для центральной
   зоны кадра (лучи <~10° от вертикали): вертикальный луч даёт lat/lon независимо
   от рельефа. Краевые пиксели надирного кадра над крутым склоном — обычные косые
   лучи: съезд ≈ ошибка DEM × tan(отклонения), правила ступеней 2/4. Объект у края —
   искать кадр соседнего галса, где он ближе к центру.
4. **Трассировка луча**: `analysis/.venv/bin/python analysis/geoproject.py cast <видео> <t> <px> <py> <f>`
   — печатает координаты точки, дистанцию и GSD (метры-на-пиксель).
   Фокусное — `geoproject.py focal <видео> T0 T1` на интервале чистого
   панорамирования без зума; если шумит — методика `docs/focal-length-calibration.md`
   (паспортные границы M30T 4026–14315 px при 1920×1080, медиана+MAD).
   Обязательно прогнать вилку фокусного и вилку DEM ±30 м (образец —
   `analysis/project_map_points.py`, вердикты ok/poloho/no_hit); вилка = σ точки,
   писать её в `coord`/`unc`.
5. Увод по вилке DEM >30 м (луч полого к склону) и второго ракурса нет —
   координатой **не считать**: точка остаётся на GPS дрона + ус
   `view=[азимут, наклон]`, в `coord` честная оговорка (σ до ~145 м).

Грабли привязки:
- **GPS-ловушка**: GPS дрона — позиция дрона, объект может быть до ~145 м в
  стороне (`docs/nezavisimyy-analiz/02-gps-lovushka.md`).
- **Перелёт кромки**: пологий луч (< ~10° к горизонту), проходящий выше точки
  LRF/якоря, может перелетать кромку ближней гряды и падать на следующий склон —
  плоскость через якорь даёт ошибку в ~100 м. Для таких лучей координата — только
  триангуляцией с второй позиции дрона (пиксель переносить SIFT-ом, фокусное
  SUPR-тайлов ≈ 15700 px, W-кадров ≈ 3150 px; EXIF-пересчёт занижен на ~18%).
- DEM на стене района вещей врёт до ~58 м — там высотная привязка по
  LRF-высоте известного объекта кластера, не по cast.
- Часы вертолётной Sony сбиты — вертолётные таймкоды с оверлеев не бьются.
- Нет надёжной привязки — объект в «Требуют атрибуции» реестра, а не точка
  с сомнительной координатой.

## 6. Карточка в POINTS (`analysis/viewer/build_map.py`)

```python
dict(kind="furrow", src="tg", status="open", conf=3, lat=…, lon=…, alt=…,
     name="Две борозды … (личка Геннадия)",
     coord="геопроекция луча в рельеф: дистанция 200 м, фокусное 6465 "
           "(самокалибровка, вилка ±7 м); луч полого — вилка DEM уводит до ~44 м",
     gps=[…, …, 200],          # позиция дрона + дистанция (серая связка)
     view=[108, 10], unc=45,   # ус направления камеры; неопределённость, м
     video="DJI_20260813163855_0001_Z",
     tc="4:04 (в заявке «3.54»; кадр сматчен по SIFT, 149 инлаеров)",
     who="находка Геннадия Беге (админ TG-группы), личка 14.08 (#149015); вердикта нет",
     desc="…что видно, размеры/GSD, положение относительно известных объектов…",
     imgs=["data/telegram/lichka-gennadiy-bege/149015.jpg",     # исходный скрин
           "analysis/fullframe/<слаг>/…_zoom.png"])             # наш кроп
```

- `coord` — честный текст метода привязки с вилками; `who` — кто нашёл, когда,
  номер сообщения, статус вердикта; `tc` — реальный таймкод + расхождение с заявкой.
- В `desc` обязательно оценка размера объекта по телеметрии: пиксельный размер
  на кадре × GSD из `cast`, вместе с самим GSD — «при GSD 0.4 см/пикс толщина
  1–2 см — масштаб верёвки», «предметы ~0,2–1,3 м». Размер — аргумент за/против
  интерпретации (верёвка/ледоруб/тело/камень).
- Новый вид точки — добавить в `KINDS`.
- `build_map.py` правят параллельные сессии: перед правкой проверить mtime,
  после сборки — что своя карточка выжила (`rg -c "<маркер>"`) и число точек.

## 7. Синхронизация доков

- `docs/nakhodki/README.md` — единственный источник правды координат вещей;
  производные (`analysis/findings-marks.tsv`, KML) синхронизируются вручную.
- `docs/telegram/svodka.md` — раздел открытых кандидатов.

## 8. Пересборка, проверка, деплой

```bash
analysis/.venv/bin/python analysis/viewer/build_map.py
rg -c "<маркер новой точки>" analysis/viewer/map.html
# локально: http://localhost:8077/analysis/viewer/map.html (сервер обычно уже висит)
analysis/.venv/bin/python analysis/viewer/build_dist.py
npx wrangler pages deploy analysis/viewer/dist --project-name alp-finder 2>&1 | tail -5
bash scripts/deploy_mirror.sh 2>&1 | tail -8
```

Проверка публикации: `curl -sL` (без `-L` ловится 308-редирект `/map.html → /map`
и проверка ложно фейлится); `*.pages.dev` из РФ-сети блокируется — проверять
по зеркалу `https://darazumovskiy.github.io/alp-finder/map.html` с
cache-busting `?nocache=$(date +%s)`; GitHub Pages пересобирается ~минуту.
`deploy_mirror.sh` делает push в `gh-pages` — это git-запись, на неё нужна
явная просьба/подтверждение пользователя. Секреты (`.tg_session`, `.tg_env`)
в коммиты не включать.

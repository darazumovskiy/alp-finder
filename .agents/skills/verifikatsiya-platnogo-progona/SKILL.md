# Сварм-верификация платного прогона

Проверяется **решение**, а не логистика: что именно считаем/тренируем,
верна ли концепция и её математическая реализация. Прецедент проекта —
расчёт координат, где ошибки реализации ловились по 20 итераций; на
платных прогонах столько итераций не купить. Взаимодействие с сервисом
аренды проверяет ровно один агент — стоимость.

Скилл — **оркестратор**. Сам ничего не проверяет и не делает выводов:
готовит заявку, запускает верификаторов с запечёнными промптами, механически
собирает вердикты, показывает оператору. Деньги тратятся только после
явного аппрува оператора по этой сводке.

## Рой (три агента, промпты в agents/)

1. `agents/kontseptsiya.md` — ревьювер КОНЦЕПЦИИ решения: продуктовая
   задача, общая логика подхода, допущения, известные грабли проекта,
   встроится ли результат в продукт. Читает документацию проекта.
2. `agents/matematika-realizatsii.md` — ревьювер МАТЕМАТИЧЕСКОЙ
   РЕАЛИЗАЦИИ: код решения построчно, формулы, что куда передаётся,
   единицы, системы координат, параметры модели.
3. `agents/stoimost.md` — верификатор СТОИМОСТИ: единственный агент про
   сервис аренды; смета тест-прогона и полного прогона, потолок, скрытые
   расходы.

## Железные запреты

1. **Промпты верификаторов запечены** в `agents/*.md`. Оркестратору
   ЗАПРЕЩЕНО писать, дополнять, сокращать или перефразировать их — иначе
   исполнитель убедит проверяющих, что всё ок. Разрешена ТОЛЬКО подстановка
   двух плейсхолдеров: `{repo_root}` и `{zayavka_path}`.
2. **Заявка — единственный вход роя.** Всё, что оркестратор хочет сообщить
   верификаторам, он пишет в заявку по шаблону `zayavka-template.md`.
   Заявка обязана дать ПОЛНЫЙ контекст: продуктовую задачу со ссылками на
   документацию проекта, концепцию решения, математическую реализацию
   с путями к коду. Заявка — утверждения, подлежащие проверке, а не истина.
3. **Любая ОШИБКА в любом вердикте** → исправить → перезапустить ВЕСЬ рой
   заново на чистом контексте (новые Task, не resume). Частичных
   перепроверок нет.
4. **Денежные операции** (пополнение, аренда, любое списание) — только
   оператор лично либо по его явному аппруву данной конкретной операции
   с озвученной суммой. Агенту биллинг не выдаётся by design.

## Алгоритм

1. **Заявка.** Заполнить `zayavka-template.md` (концепция + реализация +
   смета), сохранить в `analysis/progon-review/<слаг>/zayavka.md`.
   Все числа — со ссылками на первоисточник (файл, команда, прайс).
2. **Рой.** В ОДНОМ tool-message запустить три `Task`
   (`generalPurpose`, фон, только чтение — в промптах это уже прописано)
   с промптами из `agents/`, подставив только `{repo_root}` и
   `{zayavka_path}`.
3. **Сбор.** Ответы сохранить как есть в `analysis/progon-review/<слаг>/
   verdict-{kontseptsiya,matematika,stoimost}.md`. Механически (без
   пересказа своими словами) собрать сводку: направление → итог (ГОДЕН /
   НЕ ГОДЕН / С ОГОВОРКАМИ) → уверенность → список ошибок.
4. **Ошибки есть** → чинить → обновить заявку → пункт 2 заново (весь рой).
5. **Все ГОДЕН** → показать оператору: сводку вердиктов с уверенностями,
   понятное объяснение простыми словами (что считаем/тренируем, как,
   сколько стоит тест и полный, потолок) — и ждать явного «да».
   Без «да» не тратить.

## Тест-прогон

Заявка обязана содержать и тест-прогон (минимальный платный кусок,
подтверждающий работоспособность всей цепочки), и полный прогон. Первым
всегда исполняется тест-прогон; его результат сверяется с ожиданием из
заявки до запуска полного.

## Чек-лист

```
- [ ] Заявка: продуктовая задача + концепция + мат. реализация + смета,
      числа со ссылками на первоисточники
- [ ] Три Task в одном сообщении, промпты — дословно из agents/*.md
- [ ] Вердикты сохранены как есть, сводка собрана механически
- [ ] Ошибки исправлены и рой перезапущен целиком (если были)
- [ ] Оператору показаны: сводка, объяснение простыми словами, суммы
- [ ] Явное «да» оператора получено ДО первого списания
- [ ] Тест-прогон исполнен и сверен с ожиданием до полного прогона
```
